# 产品需求文档（PRD）

版本：1.0；日期：2026-10-22；状态：P0 与 P1 已实现，P2 可选页面留待后续。验收证据见 [最终报告](FINAL_ACCEPTANCE.md)。

## 1. 用户问题与主流程

用户希望把一个小型编程任务交给多个职责清晰的 Agent，观察代码在审查和修复之间流转，并获得可检查的交付物。

用户输入任务 → 校验输入 → 编码 Agent 生成初稿 → 审查 Agent 输出报告 → 通过则结束；不通过则修复 Agent 根据报告修改 → 同一审查 Agent 复审 → 通过或达到修复上限 → 保存终态与产物。

编码、审查和修复使用独立角色配置及输入输出契约；允许共用一个模型提供者。角色调用必须真实消费上游输出，不能用固定文本伪装真实模型协作。

## 2. 功能需求

| 编号 | 优先级 | 需求 | 验收标准 |
| --- | --- | --- | --- |
| F01 | P0 | 任务输入 | 接收 UTF-8 任务文件；空输入、超长输入、文件不存在时明确报错，不启动 Agent |
| F02 | P0 | 编码 Agent | 输出非空 Python 源码文本、语言与实现说明，保存初始版本 |
| F03 | P0 | 审查 Agent | 消费任务和当前代码，输出判定、问题列表及理由，报告绑定代码版本 |
| F04 | P0 | 修复 Agent | 消费当前代码及未通过报告，输出新版本和问题 ID 对应的修改说明 |
| F05 | P0 | 编排 | 顺序执行；通过直接结束；不通过进入修复与复审；最多两轮修复 |
| F06 | P0 | 通信与状态 | 共享状态和消息信封含运行标识，记录各节点开始、完成或失败 |
| F07 | P0 | 输出落盘 | 每次运行独立目录，保留所有代码版本、报告、消息、状态和错误信息 |
| F08 | P0 | 离线演示 | Mock 提供直接通过、修复后通过、持续拒绝和调用失败四类固定场景 |
| F09 | P0 | 真实模型适配 | 通过独立 Provider 接口调用；缺少配置时明确报错，不静默切换 Mock |
| F10 | P0 | 基本错误处理 | 调用超时、响应格式错误、文件写入失败均返回非零退出码，避免假成功 |
| F11 | P1 | 使用体验 | 可读的阶段进度、结束摘要及结果目录路径 |
| F12 | P2 | 增强界面 | 只读结果展示页面；不阻塞首期验收 |

P0 为本项目首期必须交付，P1 为完成 P0 后的改善，P2 留待后续；项目优先级不等同于课程硬性要求。

## 3. 输入输出约束

- 输入为单文件 Python 纯函数需求；任务正文上限 10,000 个 Unicode 字符，超出直接拒绝。
- 输出以 UTF-8 保存；代码文件扩展名为 `.py`，报告和运行元数据为 JSON。
- 审查报告的 verdict 仅为 pass 或 fail；fail 必须包含至少一个问题；问题包含唯一 ID、严重度、描述和建议。
- 严重度为 blocker、major、minor；存在 blocker 或 major 不允许 pass；仅 minor 时允许通过但须保留提示。
- 审查不执行代码；格式校验不代表语义正确，人工验收样例补充验证。
- 每次审查绑定精确的代码版本；修复必须创建新版本，不能覆盖历史。

## 4. 失败与终态

run 状态为 pending、running、succeeded、failed、needs_attention。succeeded 只在有效报告判定通过且产物保存完成后写入；达到两轮修复上限仍不通过时为 needs_attention；输入、格式、调用或存储异常为 failed。

模型调用默认超时 60 秒；超时、限流或临时服务端错误允许重试一次；鉴权错误及响应结构校验失败不自动重试。修复次数与传输重试次数分别计数，日志记录每次尝试。

命令行退出码：成功 0；运行失败 1；输入或配置错误 2；需人工介入 3。入口为 `python -m se02 run --task FILE` 或 `se02 run --task FILE`，见 README。

## 5. 非功能需求

- 可维护性：领域对象不依赖具体模型 SDK，角色实现不承担调度和磁盘操作。
- 可追踪性：运行 ID、消息 ID、节点名、代码版本、时间和耗时可关联。
- 隐私：密钥仅从环境变量读取；不得写入日志或版本库；报告导出前检查任务中个人信息。
- 可重复性：固定 Mock 输入得到稳定的业务结果，时间和运行 ID 不作为确定性比较依据。
- 性能：离线小样例单次运行目标不超过 10 秒；真实模型耗时单独记录，不作固定延迟保证。

## 6. 典型用户故事

1. 演示者选择“修复后通过”场景，看到三个 Agent 的消息及代码 v1、v2，确认复审针对 v2。
2. 评审者查看失败目录，能够定位是模型异常、报告格式错误还是修复超限。
3. 开发者替换 Provider，仅调整配置与适配器，保持领域协议和编排逻辑不变。
