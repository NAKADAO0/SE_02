## 2. 模块开发任务与出口条件

| 模块 | 工作内容 | 输入与输出 | 完成条件 |
| --- | --- | --- | --- |
| M0 需求基线 | 评审目标、PRD、架构、验收范围 | 课程材料 → 本文档集 | 确认方向、P0、字段与边界 |
| M1 领域契约 | 实现数据对象、状态枚举、校验和领域异常 | 原始数据 → 有效对象或明确错误 | 错误判定、版本关系、必填字段和终态约束测试通过 |

| M3 角色模块 | 编码、审查、修复各自提示及解析 | 类型化输入 → 类型化输出 | 审查消费当前代码，修复消费报告；畸形输出被拒绝 |
| M4 编排引擎 | 顺序调度、分支、两轮修复上限、消息和状态 | Task → RunResult | 成功、跳过、修复、超限及异常路径集成验证通过 |
| M5 CLI | 输入文件、配置、Mock 选择、进度、退出码 | 用户参数 → 可读结果及目录 | 不懂内部接口的用户能按 README 完成离线演示 |
| M6 HTTP Provider | 环境变量、真实请求、超时、错误分类及一次重试 | 同一 Provider 请求 → 模型响应 | 脱敏真实冒烟记录；无配置显式失败；协议与 Mock 一致 |
| M7 交付 | 文档校准、样例、可选录屏、打包检查 | 可运行项目 → 可复现交付物 | ACCEPTANCE 中必需项逐项记录证据 |

## 3. 每个模块的开发闭环

1. 读取 PRD 中关联需求及 Design 中接口，先确定消费者和依赖。
2. 写能检出真实问题的测试：例如报告版本错配、审查拒绝后没有进入修复，避免只检查对象能否构造。
3. 实现最小功能，仅通过约定接口调用依赖；用 Mock 隔离网络。
4. 运行该模块测试及受影响的集成场景，检查异常和产物。
5. 更新实际命令、依赖与设计差异，再提交一个职责清楚的 Git commit。
6. 集成到本地工作流后检查消息关联及落盘结果；只有证据齐全才标记完成。

先完成离线端到端骨架，再替换真实 Provider；Mock 只用于流程验证，交付报告分别记录真实模型是否已验收。

## 6. Git 协作与集成

- 本次文档初始化提交到 main；代码阶段建议使用 `feature/contracts`、`feature/workflow` 等任务分支，经检查后合入。
- 提交粒度按模块和可验证行为拆分，例如 `feat: add workflow state contracts`、`feat: orchestrate bounded review loop`。
- 修改共享协议时同步修改生产者、消费者和契约测试，避免两套字段并存。
- 不提交密钥、虚拟环境、缓存、真实任务运行目录或未脱敏模型响应。
- 推送后核对本地 HEAD 与远程目标分支一致；后续若创建 PR，描述行为变化与验证证据。
